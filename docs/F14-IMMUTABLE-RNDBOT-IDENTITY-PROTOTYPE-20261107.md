# F14 read-only actor stamp — test-only immutable snapshot prototype (7 Nov 2026)

**Owner:** CosmicCuddle. **Maintainer:** CS01 Maintenance. **Status:** new independent test-only DRAFT. No F14 gameplay policy, runtime Playerbots/Core/IP changes, or feature activation.

## Problem and scope

The verified source `RandomPlayerbotMgr::IsRandomBot(Player*)` distinguishes SelfBots and checks account list plus membership in mutable `currentBots`. There is no proven concurrent synchronization for a Core map worker to invoke that method safely while Playerbots updates the bot set. The initial generation path also cannot assume a bot is already registered. **Neither a race-10/11 check nor an account-prefix check is sufficient.**

The files under `tests/` develop an alternative *publication protocol* for later investigation: trusted single-owner/lifecycle producer supplies nonzero GUID, account, unique incarnation, race10/11, non-self Playerbot AI with a headless session, known RandomBot account and active RandomBot membership. Any missing property **fails visible**. A writer mutex creates an immutable, per-GUID generation-stamped table, then publishes a read-only shared pointer under a brief independent publication mutex. Readers copy the shared pointer under that mutex and traverse the immutable table after unlocking; this avoids deprecated C++20 shared_ptr atomic free functions while supporting C++17. Eight mock map worker threads read only plain IDs from immutable table snapshots and never touch Playerbots' `currentBots`, a real `Player*`, or a real `WorldSession*`. A stale older epoch cannot overwrite a newer one, and a stale logout cannot evict a newer actor. The prototype also retains a **test-only last-accepted-incarnation high-water mark per GUID after retirement**: without it, deleting the entry from the active snapshot would allow a delayed login callback to republish the same retired incarnation.

## Strict limits and additional safety gates

- The prototype is **not included, registered, built, or linked into any runtime module**. It doesn't add an engine hook, set stage8, hide a bot/NPC, filter WHO, reset quests, or mutate any user/player data.
- A real producer must first prove positive actor provenance from its **own safe owning thread**, and define when bot membership is added, when generation transitions occur, and whether account/Playerbot AI/Headless state remains authoritative through relog.
- **A reader with a previously loaded snapshot can still see a retired actor** until its snapshot read completes. A TRUE stamp is therefore only a necessary precondition, **not** authorization to hide; it must be paired with current live session/incarnation validation on Core's actual map owner and a human-viewer rights/corpse/quest/loot/targetability decision.
- The implementation uses a full copy-on-write map on every producer update. This may be too expensive for frequent bot churn on a server with many bots and **must be benchmarked** before any runtime adoption; a generation-aware striped table or a map-owner mail queue may be preferable.
- The source-only replay fence holds the highest accepted incarnation for each GUID **for the lifetime of this test object**, even after retirement. That memory can grow without bound across distinct GUIDs and does **not** survive restart. Production needs a validated epoch source and safe garbage-collection/restart protocol; this is not a complete revocation system.
- No client object ACK, cross-thread lifetime guarantee, exact historical hidden-pair restoration or grouped-player rights is supplied.
- Every stored value here is a **synthetic assertion** from test input, not an authoritative proof that a genuine RNDBOT is in the actual world.

## Verified lifecycle source chronology — important negative boundaries

A 7 November source audit of the **historical exact Playerbots fork** identified these distinct phases. They are not permissions to hide a player:

1. `RandomPlayerbotMgr::AddRandomBots()`'s `tryLoginBot` sets the `"add"` event and calls `currentBots.insert(charInfo.guid)` *without creating a live Player or session*. The eventual `ProcessBot(uint32)` can later call `AddPlayerBot(botGUID, 0)`. Therefore merely being in `currentBots` means **selected/reserved**, not fully online or positively headless.
2. `GetBots()` separately repopulates `currentBots` from database event entries after startup. Rehydration is also **not** materialisation or login completion.
3. `PlayerbotHolder` queues the login operation after `OnPlayerLogin(bot)`. The separate `OnBotLogin` path adds a pointer to `playerBots` *before* testing `GET_PLAYERBOT_AI(bot)` for null. A sound positive stamp must wait for the actual fully verified session/AI and world admission, not infer it from this earlier insertion.
4. `ProcessBot(uint32)` has both `currentBots.erase(bot)` **before** `LogoutPlayerBot` and another path where logout is initiated **before** the erase. `OnPlayerLoginError` also removes membership. `PlayerbotHolder::LogoutPlayerBot` removes the player from its active holder and deletes its session without directly manipulating `currentBots`. A future F14 actor must be retired in every path **before any map-visible unsafe lifecycle window**, with a stable incarnation and exact game-thread ordering.

A new `tests/test_f14_randombot_lifecycle_handoff.py` suite guards the exact source chronology and explicitly **fails if it drifts**, prompting review before adding a real identity producer. These checks are an inspection of existing code, **not** tests of asynchronous runtime ordering or thread affinity. No positive F14 identity should be issued from `currentBots.insert`, `GetBots`, race/account alone or a null-AI `OnBotLogin`. Identity stamping, retirement and in-map session checks remain separate future design/implementation.

## Actual world-thread deferred login route — candidate hook location, not a proof

The same verified Playerbots source exposes a more precise lifecycle order:

1. `PlayerBotsWorldScript::OnUpdate` invokes `PlayerbotHolder::UpdatePendingLogins()`, `sRandomPlayerbotMgr.UpdateSessions()`, `PlayerbotWorldThreadProcessor::Update(diff)`, then `sRandomPlayerbotMgr.UpdateAI(diff)`. Thus pending login callbacks are drained before queued operations on this source path.
2. `OnBotLoginOperation::Execute` is an enqueued `PlayerbotWorldThreadProcessor` operation. Its `IsValid` checks `ObjectAccessor::FindConnectedPlayer` and its `Execute` selects a holder using the master account; it does **not** check headless, in-world, RandomBot membership or non-null PlayerbotAI. Therefore neither the queued operation nor `playerBots` insertion is positive identity evidence.
3. `PlayerbotHolder::OnBotLogin` first inserts into `playerBots`, invokes `OnBotLoginInternal(bot)`, **then** obtains `GET_PLAYERBOT_AI(bot)` and returns when null. Any future positive identity publisher must occur **only after this check** and independently verify `bot->GetSession()->IsHeadless()`, `bot->IsInWorld()`, genuine `IsRandomBot` with account + active set, no SelfBot/master, unique generation and current map ownership; a mere `OnBotLogin` callback does not do all of those.
4. `PlayerbotWorldThreadProcessor::ProcessBatch` removes operations from its queue while holding a mutex, **releases that mutex**, and invokes `operation->Execute()`. An eventual Core notification must not execute under the queue mutex.
5. `PlayerbotHolder::LogoutPlayerBot` currently removes the holder entry before `WorldSession::LogoutPlayer(true)` deletes the Player/AI and then deletes the session. An actual identity retirement must be ordered **before pointer deletion** across all logout/error/disable/shutdown paths, including return-on-null-AI, and an in-flight map reader must revalidate its incarnation; no retirement hook is implemented now.

Five additional source/mutation-regression conditions protect this ordering under a test-only DRAFT. They do not assert that thread affinity or memory visibility has been empirically proven, nor do they authorise an actual F14 hide; a map-owned serialized handoff is still unbuilt.

## Cross-repository source check: session expansion is not earned progression

On the pinned owner Core fork `WorldSession.cpp`, `_headless(!sock)` classifies a session as headless when its socket pointer is absent. In pinned Playerbots `PlayerbotHolder::AddPlayerBot`, the synthetic bot `WorldSession` is created with `nullptr` socket **and** raw `EXPANSION_WRATH_OF_THE_LICH_KING` session value before loading the Player. In owner IP #46, `IndividualProgressionPlayer.cpp::OnPlayerLogin` still assigns stage **0 for level <=60** to bot/excluded accounts unless the optional already-earned saved-stage preservation branch succeeds. Stage 8 is assigned for levels 61–70, stage 13 above level70; this is NOT the requested positive initial stage8 for eligible race10/11 RandomBots. `TbcRacesStartingProgression` is applied in a distinct normal-account branch, so it is not a substitute for the selected RandomBot rule.

**Consequences:** A socketless, Wrath-labelled bot session by itself neither proves a verified RandomBot **nor** establishes that the character has earned Wrath progression. The no-socket invariant cannot be used alone as F14 hide authority; the raw session expansion cannot serve as an IP stage entitlement or its replacement. Correct stage8 birth/upgrade policy still needs owner-specific eligibility, progression limit, saved-stage0–7 migration and higher-stage preservation safeguards. The new exact-SHA CI-only Core/IP read-only check is a source **gap detection**, not implementation, actual WotLK access proof, or reason to downgrade human characters. No bot character data is changed.
