## Real Core source justification

- Owner AzerothCore `PlayerStorage.cpp::Player::SaveToDB(bool,bool)` enqueues a transaction with a **void** `CharacterDatabase.CommitTransaction`; queue drainage and CharacterCache insertion do **not** acknowledge per-GUID commit outcome.
- The same owner Core supports `Player::SaveToDB(CharacterDatabaseTransaction,bool,bool)`, `CharacterDatabase.AsyncCommitTransaction(trans)`, and movable `TransactionCallback::AfterComplete(bool)` plus `InvokeIfReady()`. Stock human character creation uses the same transaction/future pattern via session lifecycle. The optional Playerbots branch instead holds only pointer-free callbacks until its existing creation queue drains and polls ready results.
- Existing `CHAR_SEL_CHECK_GUID` is a synchronous prepared pre-save GUID presence check; `CHAR_SEL_DATA_BY_GUID` provides GUID, account, name, gender, race, class and level. The optional callback performs an independent synchronous positive post-save readback of GUID/account/name/race before recording a **process-local observation bit**. Nonready callback results are deliberately discarded rather than treated as success.

## 8 November addendum — historical GUID orphan-data veto is real source work, not a cleanup

Owner PB7 `RandomPlayerbotFactory.cpp` destructive optional account-reset path deletes `characters` and then explicitly purges many orphan tables, including `character_queststatus_rewarded` and `character_queststatus`, **but does not list `character_settings`**. Exact owner Core `AccountMgr::DeleteAccount` enumerates the account's characters from `characters` before calling `Player::DeleteFromDB`, so after PB's earlier character-table deletion that normal per-character path cannot be assumed to repair orphaned settings. This is a **source-backed possibility**, not evidence the owner's live data contains orphaned rows or that any deletion option is enabled. **Do not execute, repair or extend account-cleanup SQL** without specific owner permission and backups.

Before the optional audited transaction (and only with both F14 opt-ins ON), the PB audit now requires a prior absence of the GUID in `characters` and successful **read-only COUNT(*)=0** results for **all three** existing tables: `character_settings` (potential paid receipt), `character_queststatus_rewarded` (IP earned tier quests), `character_queststatus` (active quests). A failed count query returns no result and therefore vetoes the audited path. The ordinary default-OFF `SaveToDB(true,false)` route is unchanged. No schema or data modification. **Even this extra preflight does not prove every historical GUID-linked table is absent**, so it is not permission for automatic stage8 or positive F14 concealment.
