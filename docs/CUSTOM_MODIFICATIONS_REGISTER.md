# Custom Modifications Register

## PB-F14-SOCIAL-DISPATCH-20261114 — world-thread social dispatch and RandomBot adoption guard

The existing queued `GroupInviteOperation` also receives the standard group-invite veto before its direct group creation/conversion/add. It captures both participant epochs to reject stale queued work. This preserves ordinary IP grouping enforcement for permitted personal/Altbots without classifying them as F14 social RandomBots. Same-session invite-policy changes after preflight and native/gameplay behavior remain unverified.

Lifetime audit: public Core `395b68ee` waits for map workers in `MapMgr::Update` before the PB world-operation drain, so the map-AI logout path is serialized at that pin. The installed Core and other exceptional teardown paths remain unverified; the generation lock itself does not protect Player/session lifetime.
The Player destruction hook retires login and invitation generations as an idempotent fallback if a higher-level logout path was skipped.

- **Owner:** CosmicCuddle. **Owning component:** `mod-playerbots` in its own repository.
- **Parent/source reference:** public `CosmicCuddle/mod-playerbots` master `405f81196161017eebae3ee7a612d786a3ed2a9d`; branch `feature/codex-pb-f14-social-dispatch-20261114`. Installed Playerbots/Core/IP versions are UNKNOWN.
- **Intended behavior:** bot-originated group invite, trade initiation and battleground port packets enter their session queues for world-thread handling. Group accept runs as one world-thread operation, with its existing master/strategy/summon follow-up only after the handler has established membership. The operation captures non-reusing bot and inviter login generations plus a distinct invitation generation, rejecting queued work from a previous login or invitation cycle. Personal-bot `add`, `login`, `addaccount` and the nonzero-master `AddPlayerBot` entry refuse positively identified type-1 RandomBot-account characters; own/linked alts and type-2 AddClass accounts retain their prior path. Missing character account or unresolved managed-account type fails closed.
- **Affected files:** `src/Ai/Base/Actions/InviteToGroupAction.cpp`, `AcceptInvitationAction.cpp`, `TradeAction.cpp`, `AcceptBattlegroundInvitationAction.cpp`; `src/Script/WorldThr/PlayerbotOperations.h`, `PlayerbotIdentityGeneration.h`; `src/Script/Playerbots.cpp`; `src/Bot/PlayerbotMgr.cpp`; `tests/f14_social_dispatch_source.test.js`; this Register and `docs/F14_SOCIAL_DISPATCH_CANDIDATE_2026-11-14.md`.
- **Dependencies:** pre-sync Phase-A Core23 `dbb1dd5150f330d88522a10b85e93546fff72bad` packet and hook behavior plus the isolated Core #30 v2 guild seam `8a306898bfa4dd5ee7ef5195e0b539ba05824799`; existing Playerbots `WorldSession` packet queues, `PlayerbotWorldThreadProcessor`, type-1/type-2 account assignments, character cache and source-matched IP social hook. Upstream-stage Core #28 v2 is separate. No new config, SQL, DBC or client patch.
- **Known risks:** queued packets may outlive their original action; Core revalidates the target state at drain, but only staged tests can show end-to-end behavior. The group-accept operation rechecks both login epochs, the invite, session and membership at execution. Pinned Core supplies an invitation callback, now used to distinguish same-session, same-group reinvite cycles at source/model level; staged gameplay remains unverified. A logout racing after the epoch check needs native validation. An unavailable account-type snapshot can block a managed account command. The other direct unsafe Playerbots routes remain outside this change.
- **Tests:** local Node source contracts and group-accept/account-classification models 17/17 PASS; `git diff --check` PASS. No native, ThreadSanitizer, Core link or gameplay test has run in this workspace. The staged matrix is in the candidate note.
- **Live status:** DRAFT only, NOT MERGED and NOT DEPLOYED. F14/Paid remain OFF.
- **Decision:** owner-approved RandomBot non-adoption policy in [coordination Issue #13](https://github.com/CosmicCuddle/Naxxramas-Server-Coordination/issues/13#issuecomment-6867335447); CS01 accepted the four-route dispatch candidate in [Issue #13](https://github.com/CosmicCuddle/Naxxramas-Server-Coordination/issues/13#issuecomment-6866003156) and assigned this lane in [Issue #51](https://github.com/CosmicCuddle/Naxxramas-Server-Coordination/issues/51).
