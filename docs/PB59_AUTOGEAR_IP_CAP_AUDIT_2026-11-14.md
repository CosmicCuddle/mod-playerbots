**Status:** source audit and default-off, fail-closed implementation candidate on PB `3a9e39f1` and IP `05ff032b`. Command gear outcomes remain unchanged with the new option disabled; enabling currently refuses all AutoGear/BiS commands. Tracked in [coordination Issue #59](https://github.com/CosmicCuddle/Naxxramas-Server-Coordination/issues/59).

## Commanding player and IP authority

`PlayerbotAI::HandleCommands` resolves the sender's GUID and checks command permission before passing the sender to `ExternalEventHelper`. `ChatCommandTrigger` retains the GUID and puts it in the event. The AutoGear actions must consume a cache-only IP snapshot keyed by that GUID; re-resolving and dereferencing a human on the bot's foreign map thread is unsafe. `GetMaster()` is not necessarily the command sender; the bot's account or stage is not authoritative.

IP currently exposes `GetPlayerProgressionFromQuests(Player*)` and `GetEffectiveProgression(Player*)`, but neither is safe for this foreign-map command path. Raw progression records completed content; effective progression enforces paid expansion access. A raw-13/effective-12 player has completed Kil'jaeden but lacks Wrath access; raw-13/effective-13 has the same completion plus Wrath access. Claude is developing a versioned cache-only snapshot with both values, full GUID, session epoch and generation in the IP lane. Unknown snapshots deny before gear mutation; native linking still needs verification.

Map-thread safety: current IP `GetEffectiveProgression` can reach `GetAccountMatch` on a Paid-active raw-stage-13+ cache miss, which performs blocking Auth DB reads. Direct `Player*` dereferences also cross map ownership. The command refuses all enabled requests before these reads until the snapshot API and external quest-marker invalidation gap are resolved.

## Cap propagation audit

| Command route | Current behavior | Required cap point |
| --- | --- | --- |
| `autogear`, quality, numeric, `reset`, `match` | `AutoGearAction::Execute` computes `ilvlCap` from `AutoGearScoreLimit` (`0` means unlimited), then calls `PlayerbotFactory::AutoGear` | Resolve a nonzero effective cap before argument parsing; use the stricter of configured and stage caps. Reject missing human/IP context before `reset` destroys gear. |
| `autogear bis`, numeric BiS | `BisGearAction::Execute` uses `AutoGearScoreLimit` for explicit argument validation and BiS lookup | Apply the same effective cap before BiS lookup or any gear/bag deletion; keep fallback at that cap. |
| BiS fallback | `RunAutogearFallback` calls `PlayerbotFactory::AutoGear` | Reuse the already checked cap; do not recompute from bot/master state. |

The factory's `ilvl` argument is converted to a mixed gear-score limit using the requested quality. In `InitEquipment`, grey/white fallback candidates can skip that score check. Therefore, merely reducing the `ilvl` argument does **not** enforce a hard item-level maximum. A separate command-scoped raw `ItemTemplate::ItemLevel` ceiling must also reach candidate selection, without changing non-command random-bot factory behavior. The BiS lookup searches downward from the requested row, but individual BiS item templates still need an item-level ceiling before equipment and bag destruction. Existing class/spec/eligibility and scoring paths should otherwise remain intact.

## Equipment planning dependency

Storage staging scope now preserves body/tabard following CS01 review. `ValidateEquipmentStorage` checks that the plan covers every currently occupied combat equipment slot exactly once, each GUID/source still matches, destinations are distinct empty inventory locations in existing bags/backpack, and Core still permits unequip/storage with an exact single destination/count. Dead/out-of-world, trade/loot, changed source, added equipment, missing bag and occupied destination states deny. Preparation invokes this validator before publishing its output; future commit must invoke it again without a yield before final authorization B. No command calls the preparation/validation prototype yet.

Core commit audit at `21ff1973`: `Player::SwapItem`'s empty-inventory move calls `RemoveItem`, `StoreItem`, `UpdateTitansGrip` and `OnPlayerUnequip`. `RemoveItem` changes durations, item-obtain spells, item-set bonuses, item mods and visible slots. A sequence of inverse swaps cannot be claimed to roll back script callbacks or already-sent updates. The current candidate therefore contains no move/commit implementation. Native integration must exercise callback/reentrancy and failure injection, item identity/enchant/socket/durability/random-property retention, source/destination changes, full/specialized bags and two-hand/offhand before this can be treated as a reversible command. Bounded synchronous execution alone does not establish rollback.

`PlayerbotFactory::PrepareEquipmentStorage` is a runtime preparation prototype, not yet invoked by commands. On the bot-owning thread it validates unequip eligibility and reserves distinct currently empty backpack/equipped-bag slots using Core's explicit-slot `CanStoreItem` checks. It records original item GUID/source and destination, preserving body/tabard and excluding equipped bags. No item is moved, created, merged or destroyed. Output is empty on any failure; a successful empty plan means the bot was already stripped. Reservation is greedy and may conservatively fail where a different specialized-bag assignment could succeed; that is an infrastructure preservation outcome, never proof of no suitable equipment. Stack merging, bank/mail and new bag capacity are excluded. Commit still needs whole-plan source/destination revalidation, final snapshot B and a reversible move implementation with failure recovery, without a yield. No successful preflight alone authorizes mutation. Native inventory fixtures and gameplay remain open.

Latest sender-leveling requirement: propose capturing floor average raw equipped ItemLevel on the sender's owning thread, excluding body/tabard and treating absent/zero data as unknown. This averaging choice and empty-slot/heirloom policy are not approved defaults. The sample needs session/publication identity and freshness validation at B, paired with raw/effective progression; no bot-thread sender dereference. Coordinate its publication contract with the IP provider before command integration. Leveling versus endgame boundaries must be explicit at 60/70/80; no curve is inferred here.

CS01's latest staging direction defines final matching Known snapshot B (session/revision) as command authorization linearization, followed by synchronous bounded mutation on the bot-owning thread without a yield or foreign Player access. Later progression changes are ordered after the command; a later snapshot C is diagnostic only. This supersedes the earlier requirement to prevent all post-B progression changes. It does not permit multi-tick mutation or autonomous correction. The runtime cap gate still denies until preparation and reversible commit are integrated.

`AutoGearSlotPolicy.h` now supplies the existing level search rules to both `InitEquipment` passes. Production binds Core equipment constants; the independent fixture covers all thresholds and expansion-level boundaries. Searchable slots: levels 1–4 chest/legs/feet/mainhand/offhand/ranged; levels 5–19 add shoulders/waist/wrists/hands/back; levels 20–29 add both fingers; levels 30–49 add head/neck; levels 50–80 add both trinkets. Body/tabard are excluded at every level. This is the existing factory search matrix, not the final class-specific mandatory-set definition. Offhand is optional when a two-handed plan excludes it (unless Titan Grip permits it); ranged and weapon eligibility still depend on class/skills and item checks. No class slot requirements or new leveling curves are inferred from the count alone.

At PB branch parent `3a9e39f1`, reset and BiS fallback destroy all equipped items before factory selection. BiS also destroys equippable bag items before running AutoGear. In `InitEquipment`'s second-chance pass, a slot's equipped item is destroyed before checking whether `items[slot]` is empty or any candidate passes `CanEquipUnseenItem`. A valid progression cap does not establish that replacements exist. The current enabled command gate denies, so the new policy cannot reach these mutations yet.

Before enabling capped reset/BiS, selection must produce a replacement plan without deleting or moving items or granting reputation. The plan must record item IDs, random properties, destination slots, cap authority and the bot inventory state it was computed against. Eligibility must account for unique-equipped pairs, two-handed/offhand conflicts, class/race/skills, reputation and storage constraints across the whole plan. A candidate list alone is not proof of a successful replacement. Existing autonomous factory behavior requires separate regression review before changing shared selection.

The latest owner decision in Issue #59 supersedes the earlier preserve-on-no-candidate policy: a genuine no-suitable-set result under valid authority requests an intentional stripped state. Unknown/revoked authority, invalid policy, stale inventory and infrastructure/allocation/persistence failures preserve existing gear. `AutoGearCommandOutcome.h` models only this decision; it performs no mutation and cannot authorize deletion. The enabled runtime gate still denies all requests pending integration.

Proposed strip semantics for peer/owner review: affect equipment slots only, excluding equipped bags and unrelated inventory/bank/mail; use the same command authorization for personal/Altbots and RNDBOTs. Prefer moving original item instances into available backpack/bag slots so the stripped appearance is reversible. Preflight storage for the entire equipped set; if storage is insufficient, classify it as an infrastructure failure and preserve everything. Do not silently mail items, destroy originals, grant capacity, or strip autonomously. Destroying equipped items on full bags would be a separate irreversible choice and is not implemented. A legitimate no-suitable-set result must come from complete validated search, not the current factory's probabilistic candidate sampling or its low-level intentionally skipped slots. Exact mandatory slots by class/level remain a review item.

Leveling eligibility must combine the sender's raw tier/effective era cap with the bot's own level and `CanUseItem`/equipment constraints across 1–60, 61–70 and 71–80. The current factory starts its required-level search at the bot's level, uses armor/weapon checks and mixed-score limits, and optionally excludes expansion item-ID ranges. RequiredLevel alone does not prove item source era; high-ilvl low-required-level items and source-ID heuristics need installed item-data review. No new leveling cap curve or production tier values are inferred. Required scenarios: low-level bot with advanced sender, new-era leveling before raid completion, unpaid era boundary, and endgame at 60/70/80.

Required scenarios include zero eligible candidates, all candidates above cap, empty second-chance lists, paired unique items, two-handed weapons, full bags, failed item creation, and authority invalidation after planning. The execution/authorization contract must cover the mutation rather than only comparing snapshots before it.

Search completeness audit: `RandomItemMgr::GetEquipmentNew` returns an exact normalized-level/inventory-type cache bucket. `BuildCacheEquipNew` excludes qualities above epic and class-restricted quest rewards; quest rewards are indexed using the maximum of item RequiredLevel and the first processed qualifying quest's level, whereas other items use RequiredLevel. These are candidate-generation policies, not evidence that every item the bot could equip was inspected. The factory then samples candidates, stops searching once it has enough candidates, and may lower requested quality randomly. Its main pass also destroys the current item early when `second_chance` is true, before candidate search, in addition to the secondary-pass risk above. A command planner must define its accepted item universe and required slots, enumerate it deterministically, and distinguish exhaustion of that universe from missing/uninitialized cache or interrupted work. Until that is implemented, `ResolveNextStep` requires explicit `searchComplete=true` before a no-set result can request stripping; the default preserves gear. This boolean is a planner contract, not proof or runtime authorization.
