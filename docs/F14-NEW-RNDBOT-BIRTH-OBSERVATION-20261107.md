**Owner:** CosmicCuddle. **Component:** owner Playerbots fork, child of [DRAFT #1](https://github.com/CosmicCuddle/mod-playerbots/pull/1) at `ffdeb199d4ba5a058cf2176139e7cb5c7e19755c`. **Default:** `Playerbots.F14TrackNewRandomBotBirth = 0`, unchanged live / no merge. **No SQL, actual character DB, client, Core or IP changes.**

## Source-level behavior introduced on this development branch

1. **Creation event (birth CANDIDATE):** On `RandomPlayerbotFactory::CreateRandomBots`, after `SaveToDB(true,false)` is enqueued and the character cache entry added, an OFF-guarded call records only a numeric GUID + account + race for a newly CREATED character. It rejects non-TBC races, zero IDs, duplicates or >16,384 candidates; no old bot or existing character is registered.
2. **Verified login observation:** Following queued world-thread `OnBotLoginOperation` and after `PlayerbotHolder::OnBotLogin` verifies that a nonnull PlayerbotAI exists, an OFF-guarded call checks a live in-world headless session, race10/11, existing positive `IsRandomBot(Player*)`, and an exact matching same-process creation candidate. It atomically consumes each matching candidate **once**. It never calls into IP, changes a quest stage, logs player identifiers, filters WHO or hides a character or creature.
3. **Retire:** On `LogoutPlayerBot`, `DisablePlayerBot` and `RemoveFromPlayerbotsMap`, the same optional diagnostic marker becomes permanently retired for the rest of that process. This occurs before session deletion in the audited logout path; repeat callbacks cannot re-admit it. All stored content is plain integers and flags protected by a short mutex; never stores `Player*`, `WorldSession*` or `PlayerbotAI*`.
4. **No persistence:** The map is in RAM and cleared on every Worldserver restart. An older bot born before the probe was enabled, or born in a previous process, fails closed. `SaveToDB(true,false)` can be **asynchronous**, so even a recorded creation candidate is **not proof of a committed character row or owner-paid entitlement**.
5. **No behavioural change with default OFF:** extra code is bypassed by a default-false config flag. Even with the flag ON for a disposable offline test, it is **only diagnostic**; it cannot make stage8, send a packet, hide NPCs or fix the `AT_LOGIN_FIRST` mismatch.

## Tests, risks and future integration

- `tests/test_f14_new_randombot_birth_probe_source.py` checks exact real hook ordering, OFF config, positive gates, no DB/paid/IP/visibility code. Native `tests/f14_new_randombot_birth_probe.cpp` compiles the **actual production observer header** in GCC/Clang C++17 and C++20, normal/NDEBUG (eight variants), tests incorrect account/race/human/Altbot, missing positive flags, duplicate/replayed admission, logout-before-admission and eight concurrent workers. ThreadSanitizer checks the same header. **Not** a full Worldserver/gameplay test.
- An in-memory observation is **not yet a trusted first-time character creation transaction**. Future positive F14 stage8 requires dedicated durable creation provenance, successful character DB commit validation, a restart-safe generation, an approved old saved stage0–7 migration policy, confirmation of world TBC/cap and paid-era exception, and protected IP caller logic. It also requires map-owner replay/old-snapshot visibility rights, client update acknowledgement and corpse/loot restoration. Do not convert this observer result to an entitlement or hide a human/NPC.
- Bot creation currently deliberately uses `AT_LOGIN_NONE` rather than normal Core `AT_LOGIN_FIRST`, so do not reuse that human flag.
- Risks: full module native compilation and actual world-thread/map-thread ordering not proved; a bot may be created at startup before its character DB commit and never materialise; pending candidates remain until process restart; the 16,384-entry bound is arbitrary and fail-closed; true RandomBot identity relies on a manager set that must **not** be read from map workers.
